# S3 storage

Set `VAULT_STORAGE_IMPL=s3` to store document content through the S3 API.
S3 is the default backend when this setting is omitted. Metadata and audit data
continue to use MongoDB.

Configure the application with these environment variables:

| Variable      | Default                 | Purpose                            |
|---------------|-------------------------|------------------------------------|
| `S3_ENDPOINT` | `http://localhost:5000` | Custom S3-compatible endpoint      |
| `S3_KEY`      | `testing`               | Access key for a custom endpoint   |
| `S3_SECRET`   | `testing`               | Secret key for a custom endpoint   |
| `S3_BUCKET`   | `anv`                   | Bucket containing archived content |
| `S3_REGION`   | `eu-central-1`          | Region used by the S3 client       |

Provision the bucket before archiving content. The application uses path-style
requests. With a nonempty `S3_ENDPOINT`, it uses that endpoint and static credentials
from `S3_KEY` and `S3_SECRET`. To use the AWS regional endpoint and the SDK's default
credentials provider, set `S3_ENDPOINT` to an empty string and configure `S3_REGION`
and `S3_BUCKET` for the target bucket. The development Compose stack explicitly sets
the endpoint to Moto; configure the application container separately to use another service.

The backend supports content encryption, plaintext checksums and key versions.
Uploads stage content in a single private temporary file, encrypting it while writing
when enabled. The checksum is calculated on the original plaintext stream; the staged
file is streamed to S3. Allow sufficient temporary disk space for concurrent uploads. See [Encryption.md](Encryption.md) for encryption settings.

Changing the backend does not migrate existing binaries; validate a separate
archive/download/restore cycle before switching an existing vault.

## Docker development stack

The S3 development stack uses Moto as a local S3 emulator. From the repository root,
start it with:

```bash
./vault.sh start --s3
```

S3 is also the default for `./vault.sh start`. The launcher creates the external
volumes required by the development services, builds the application and starts
the stack. The Moto provisioner creates the `anv` bucket with the development
credentials and region shown above.

The application reaches Moto at `http://anv-motoserver:5000` inside Docker.
The service is also published at `http://localhost:5000` for an application running
on the host. `MOTOSERVER_IMAGE` in `docker/.env` selects the emulator image.
The provisioner uses the fixed development bucket `anv`; creating another bucket
and configuring the application to use it requires a corresponding Compose override.

Inspect logs or stop the stack using:

```bash
./vault.sh tail --s3
./vault.sh stop
```

Stopping retains the external data volumes. `./vault.sh purge --s3` removes those
volumes as well. Moto has no persistent data volume in this configuration, so do
not rely on it to retain archived objects after its container is removed. This
stack is intended for development and functional testing.

On Windows, `vault.bat start` uses the S3 development stack.
Stop the current development stack before switching backend.

## Integration tests

After starting the development stack, run `mvn test -Ps3` or simply `mvn test`.
The Maven profile selects S3 for the Spring application started by the tests,
using the host endpoint `http://localhost:5000`. Select the matching profile when
using another backend: `-Pgridfs` or `-Pozone`.

## S3 smoke test

Run the isolated end-to-end suite with:

```bash
./smoke-tests.sh --s3
```

S3 is also the default for `./smoke-tests.sh`. On Windows, use
`smoke-tests.bat --s3`. Add `--keep-running` to retain services for inspection,
or use `--all` to test S3, GridFS and Ozone together.

Each backend runs the same plaintext and encrypted archive/download/restore checks,
including empty files, Unicode filenames, checksums and restore retries.
The suite uses the shared `anv-smoke` project with isolated volumes, databases
and buckets, without host ports or external development data volumes.

See [SmokeTest.md](SmokeTest.md) for reports, diagnostics and cleanup.
